# M2-01 グラフ構築・指標・レイアウト・配信データの書き出し

## 目的

参照の一覧から法令グラフを作り、指標、法令ファミリー、コミュニティ、1枚の地図のためのレイアウトと「大陸」の形を計算して、Web契約（00）の形で書き出す。

## 並行性と依存

- 前提: `00-data-contract.md`、`README.md`。
- 依存: `data/corpus/{snapshotId}/`（m1-01）と、`data/refs/{snapshotId}/` の最初の全件版（m1-02）。精度が目標に届く前の版で作り始め、抽出器が更新されたら作り直す。判定に出すのは `manifest.json` のある最終版から作ったものだけ（受け入れ条件の「入力」）。
- m2-02（UI）とは契約だけでつながる。UI は仮データで先に進んでいる。書き出しができたら coordinator に知らせ、UI を本物のデータに切り替えてもらう。
- 検査用の `validate-web-data.ts` は m2-02 が `shared/` に作る。まだなければ、00 の受け入れ条件を自分のテストで確かめ、できたら差し替える。

## 入力と出力

- 入力: `data/corpus/{snapshotId}/laws.json`、`repealed.json`、`text-*.jsonl.gz`（条の pid と順序だけ使う）、`data/refs/{snapshotId}/`、`data/eval/{snapshotId}/report.json`（あれば `manifest.eval` に入れる）。
- 出力: `data/graph/{snapshotId}/`（中間、形式は自由）、`data/web/{snapshotId}/`（00 の Web契約の全ファイル）、`data/web/latest.json`、`media/m2/map-overview.png`（地図全体の画像。レビュー用）、`media/m2/layout-check.png`（配置の判定用の基準描画）。
- コード: `pipeline/src/graph/`。コマンド `npm run graph -- --snapshot {snapshotId}`（グラフと指標とレイアウト）、`npm run export -- --snapshot {snapshotId}`（書き出し）。
- ライブラリ: graphology、graphology-metrics（PageRank）、graphology-communities-louvain、graphology-layout-forceatlas2、graphology-layout-noverlap、d3-contour、polylabel、culori（色の変換）、zod。

## ノード

- 施行中の全法令（`laws.json`。`notYetEffective` を含む）。
- ゴースト: 廃止法令のうち、施行中の法令から本則系で1回以上参照されているもの（`repealed.json` に lawId があるもの）。`status: repealed`、`revisionId: ""`。
- 改正法（`amendingLaw`）と不明（`unknown`）はノードにしない。件数は `data/graph/{snapshotId}/stats.json` に残す。
- 地図の表示名 `label`: e-Gov の略称（`abbrevs`）の最初のものが法令名より短ければそれ。なければ法令名。16字を超えたら15字で切って「…」を付ける。法令名の先頭の「明治五年太政官布告第三百三十七号（改暦ノ布告）」のような番号部分は、括弧の中の名前があればそれを使う。
- 検索用 `aliases`: e-Gov の略称、JLaw の略称辞書で当たるもの、本文で定義された略称のうちほかの法令で3回以上使われているもの。重複を除き、最大8個。

## エッジ

- 他法令への参照（`tgtLaw` があり、参照元と違う法令で、どちらもノードにあるもの）を法令ペアごとに集計する。
- `mainRefs` = 部が `main`、`enact`、`appdx` の言及数。`supplRefs` = `suppl`、`supplAmend` の言及数。
- `kindMask`、`domKind` は 00 の定義どおり。
- `intraFamily`: 両端の `family` が同じなら1。

## 法令ファミリー

- 親を決める: 参照元が政令・府省令・規則・勅令・その他のとき、`basis` の言及数×3 + `implements` の言及数 がいちばん大きい参照先（法律・憲法・政令・勅令に限る）を親にする。どちらもなければ、法令名がその法令名で始まる法律（例: 「河川法施行令」→「河川法」）のうち、本則系で参照しているものを親にする。それもなければ親なし。
- 根: 親をたどり、法律か憲法に着くか、親がなくなるところ。循環したら、循環に入った最初の法令を根にする。
- 根が自分なら `family` は自分の lawIndex。

## 指標

- `inLaws`、`outLaws`、`inRefs`、`outRefs`: 本則系だけで数える。
- PageRank: 本則系の言及数を重みにした有向グラフ（向きは参照する側 → 参照される側）。減衰係数0.85、許容誤差1e-9、最大200回。
- `bridge`: その法令を本則系で参照する法令の分野の数（自分の分野を含む）。
- コミュニティ: 本則系の重みを足した無向グラフで Louvain（解像度1.0、乱数は種固定）。
- `delegations`: m1-02 の `law-features.jsonl` から。

## レイアウト

ワールド座標は、全体がおおむね −1000〜1000 に入るようにする。乱数はすべて `mulberry32` で種固定。グラフへのノードの追加は lawIndex 順、エッジの追加は（小さい lawIndex, 大きい lawIndex）の昇順にする（FA2 の結果が追加順で変わるため）。

方式は「分野の円を結びつきで詰めて並べ、その中で法令を分野ごとに力学配置する」（Group-in-a-Box の力学版）。法令全体を1回の ForceAtlas2 にかける方式は使わない。この引用グラフは分野をまたぐペアが 66%（重みで 33%）あり、上位30法令が重みの 34% に触れるので、全体の力学配置だけでは分野が混ざった毛玉になる（理由と実測は `internal/reports/m2-01-layout-diagnosis.md`）。

法令ペアの重みは、向きを無視してペアごとに `w = log2(1 + mainRefs) + (basis か implements を含めば 2)` を足したもの（両向きあれば両方の和）。`mainRefs = 0` のペアは使わない。

1. **分野の円の配置**
   - 分野 i と j の流れ `F_ij` = 2分野の間の本則系の言及数（向きを無視して合計。自分の分野は除く）。`T_i = Σ_j F_ij`。結びつき `a_ij = F_ij / sqrt(T_i × T_j)`。
   - 分野の円の半径 `ρ_i = 10 × sqrt(n_i)`（`n_i` はゴーストを含む法令数）。
   - ばね: 各分野から `a` の大きい順に上位5分野へ張る（両側から張られても1本）。強さ `k_ij = sqrt(a_ij / max a)`。加えて、同じまとまりの分野どうしにすべて強さ1のばねを張る（上と重なっても別に足す）。
   - 中心への引き: `g_i = 0.01 × T_i / mean(T)`（流れの多い分野ほど中央に来る）。
   - 反復 1,500回（t = 0〜1499）。`s = 1 − t/1500`、半径の倍率 `γ = min(1, 0.15 + t/900)`。毎回、変位 `D` を0にしてから:
     - 各ばね: `d = |p_j − p_i|`、`L = γ(ρ_i + ρ_j)`。`D_i += 0.25 k (d − L)(p_j − p_i)/d`、`D_j` には逆向きに同じ量。
     - 各分野: `D_i −= g_i p_i`。そのあと `p_i += 0.5 s D_i`。
     - 衝突: 3周。すべての対で `d < 1.02 γ(ρ_i + ρ_j)` なら、足りない分を半分ずつ離す。
   - 初期位置は種 `seed` の乱数で [−150, 150]² に一様。`seed = 1〜16` を全部試し、`adjFlowShare + 0.5 × groupContig`（定義は「地図の判定」）が最大のものを採る。同点は小さい seed。
   - 入れ替え改善: 同じまとまりの分野の対（i < j の順）で位置を入れ替え、衝突を解く（40周。毎周、全体を中心へ 0.2% 縮めてから全対を押し離す）。`J = Σ F_ij × max(0, d_ij − ρ_i − ρ_j)` が 0.1% 以上減れば採用する。採用がなくなるまで、最大6周。
   - 実データの試作値: `adjFlowShare` 0.285、`groupContig` 0.84。
2. **分野の中の配置**（分野ごとに独立。種は `20261008 + 分野id`）
   - その分野の法令（ゴーストを含む）と、分野内のペアだけでグラフを作る。エッジの重みは `0.05 × w`。graphology の FA2 はノードの質量を「1 + 重み付き次数」にするので、重みを小さくしてハブの質量を抑える（質量が大きいと斥力が強くなり、ハブとその周りが外へ飛ぶ）。
   - 初期位置は半径100の円内に一様。ForceAtlas2（`linLogMode: true`、`outboundAttractionDistribution: false`、`scalingRatio: 0.05`、`gravity: 1`、`strongGravityMode: false`、`slowDown: 2`、法令が500を超える分野だけ `barnesHutOptimize: true`・`barnesHutTheta: 0.6`、600回）。`outboundAttractionDistribution` は Gephi の「ハブを外へ」なので使わない。
   - 大きさ合わせ: 重心を原点に移し、原点からの距離の95パーセンタイルが `0.92 ρ_c` になるよう拡大縮小する。
   - 向き: `u_ck` = 自分の分野 c の円の中心から相手の分野 k の円の中心へ向かう単位ベクトル。各法令の「外への引き」`e_i = Σ w × u_ck`（法令 i の、分野をまたぐペアすべてについて足す）。鏡映 `m ∈ {1, −1}`（y に掛ける）と回転 θ を、`|Σ p_i·e_i|` を最大にするよう選ぶ（`θ = atan2(Σ p_i×e_i, Σ p_i·e_i)`。2つの m で大きい方。同点は m = 1）。
   - 寄せ: `p_i += 0.5 × s_i × ρ_c × e_i/|e_i|`、`s_i` = その法令の分野外の重み ÷（分野外 + 分野内の重み）。`e_i = 0` なら動かさない。
   - 柔らかい囲い: 中心からの距離 `r > 0.92ρ_c` のとき `r' = 0.92ρ_c + 0.08ρ_c × tanh((r − 0.92ρ_c)/(0.08ρ_c))` に縮める（円周に法令が貼り付く弧を作らない）。
   - 最後に分野の円の中心を足す。
3. **正規化**: 全体の外接矩形の中心を原点に移し、長い辺が2,000になるよう拡大縮小する。
4. **重なりの解消**（正規化のあとのワールド座標で）: 半径 `r = 0.75 + 0.4 × sqrt(articles)`（ゴーストは0.75）。noverlap（`margin: 0.5`、`ratio: 1.1`、500回）のあと、格子（1辺 = r の最大の2倍）で重なる対を lawIndex 順に探し、`(r_i + r_j + 0.1 − d)/2` ずつ離す。重なりが0になるか300周で止める（noverlap だけでは実データで数百対残る）。同じ点にある対は lawIndex から決まる向きに離す。x、y、r を小数1桁に丸める。
5. 大陸: 分野ごとに、その分野の法令の位置から `d3-contour` の `contourDensity`（`bandwidth: 18`、`cellSize: 4`、重みは1）を作り、その分野の法令の90%以上を囲む最も高い密度の閾値の等値線を大陸の形にする。ダグラス・ポイカー（許容2）で点を減らす。面積が全体の0.5%未満の小島は、その分野の法令が1つもなければ捨てる。まとまりの輪郭は、まとまりの法令全体で同じ処理（`bandwidth: 30`）。
6. ラベルの位置: 大陸のいちばん大きな多角形に `polylabel`（精度1）。
7. 分野間の流れ: 分野 → 分野の本則系の言及数。自分の分野を除き、多い順に300行。

## 書き出し

- `laws.json` の並び順は 00 のとおり（status → category → lawId）。lawIndex はこの順番。
- `refs/{lawId}.json`: 他法令への参照と他法令からの参照。並び順と切り詰めは 00 のとおり（相手の法令ごとに先頭 K 行、そのうえで各方向5,000行）。K は20から始め、`data/web/{snapshotId}/` 全体が 150,000,000 バイトを超えたら 15、10 の順に下げて作り直す。使った K を `layout-report.json` の `refsPerPartnerCap` に書く。`ctx` は本則以外のときだけ、文から作る（前30字＋⟦言及⟧＋後30字）。
  - 見込み（最終 refs の行数 × 前回の書き出しの1行あたり約147バイト。`refs/` だけの量で、ほかのファイルが約9MB 加わる）: 切り詰めなし 279MB、各方向5,000行だけ 249MB、各方向500行 155MB（どれも超過）。相手ごと20行なら 128MB、15行なら 117MB。
- 全体の大きさは、展開した `data/web/{snapshotId}/` のファイルサイズの合計（`du -sb` 相当）で測り、150MB = 150,000,000 バイトとする（MiB で測らない）。
- `manifest.json`: `files` に全ファイルのバイト数と sha256。`attribution` に「出典: e-Gov法令検索（https://laws.e-gov.go.jp/）の法令データを加工して作成」と「略称辞書の一部に JLaw-CiteGraph（Apache-2.0）を使用」を入れる。
- 最後に `validate-web-data.ts` を通す。通らなければ書き出しを失敗にする。
- 地図全体の画像: 書き出したデータから、大陸・エッジ（`mainRefs` 上位2万本、加算合成、不透明度0.04）・ノードを 3000×3000 の PNG に描く（`@napi-rs/canvas`）。`media/m2/map-overview.png` に置く。見た目の確認用で、合否には使わない。
- 配置の判定画像: 下の「地図の判定（配置）」の基準描画を `media/m2/layout-check.png` に置く。

## 地図の判定（配置）

ここで判定するのは「配置そのもの」（`laws.json` の x、y、r と、それから作る大陸）だけ。線の見せ方は3件目で扱う。

### 3件目との境目

- この仕様（2件目）: 分野の円の配置、分野の中の法令の配置、重なりの解消、正規化、大陸とラベルの位置。判定は下の基準描画と数値だけで行う。UI のスクリーンショット（`media/atlas/*.png`）では判定しない。
- 3件目: エッジの束ね（bundling）、ズームに応じた線の間引き（LOD）、線の不透明度・太さ・色、ラベルの出し方、deck.gl のレイヤー設定。合否は `m2-02-atlas-ui.md` の「見た目の判定（線とラベル）」で決める。2件目の作業ではこれらを変えない。基準描画の線が多く見えることは2件目の不合格理由にしない（配置で決まる「線の長さの分布」だけを見る）。

### 基準描画（`media/m2/layout-check.png`）

- B（中）: `mainRefs > 0` の全エッジを直線、白、不透明度0.006、太さ1px、加算合成（`lighter`）。

### 見た目の条件（coordinator が画像で判定する）

- V1（A）: 50分野が別々の島に見える。中央が空いた輪になっていない。島の中が格子模様（hex）や円周に貼り付いた弧になっていない。同じまとまり（似た色）の島がだいたい隣り合う。
- V2（A）: 白い輪（ハブ）が島の中にあり、地図の外周や海に出ていない。多くが地図の内側半分にある。
- V3（B）: 明るいところが島の上にある（線が島で終わる）。`layout-ref-e-ring.png` の B のような、空の中央を弦が横切る網になっていない。
- V4（C）: `layout-ref-e-ring.png` の C より明らかに暗い。空の中央を弦の網が一様に覆う形になっていない。

## 受け入れ条件

- 入力: `data/refs/{snapshotId}/manifest.json` がある最終版から作る。`layout-report.json` の `refsFingerprint` が、その manifest の `corpusSha256` と `createdAt` に一致する（20261009 では `createdAt` 2026-10-21T03:12:51.255Z）。古い refs から作ったものは判定しない。
- 決定性: 2回、別々のローカルの作業場所（store の外）に `graph` と `export` を最初から作り、`data/web/{snapshotId}/` の全ファイル（refs を含む）の sha256 を比べて全部一致する。ファイル数、一致数、「相対パス\tsha256」を並べた一覧の sha256 を `layout-report.json` の `determinism` に書く。store へは一致を確かめた後に1回だけ写す（tar でよい。`refs/` を一部だけ写した状態にしない）。
- 規模: ノード 9,000 以上、エッジ（法令ペア）55,000 以上。
- 分野のまとまり: 法令の85%以上が、自分の分野の大陸の中にある。分野内のエッジの長さの中央値が、分野をまたぐエッジの長さの中央値の半分以下。
- 重なり: ノードの円どうしの重なりが、ノード数の1%以下。
- 配置: 「地図の判定（配置）」の M1〜M11 をすべて満たし、V1〜V4 を coordinator が満たすと判断する。担当は数値の達成・未達だけを書き、見た目の条件を自分で合格にしない。満たさないときに別の配置へ黙って切り替えない（`categoryFallback` のような切り替えは置かない）。満たせなければ、満たせない項目と値を報告して止める。
- ファミリー: 「施行令」「施行規則」で終わる法令の90%以上に親がある。抜き取り20件（種固定）を本文で確かめ、18件以上が正しい。
- サイズ: 00 の上限（初回5ファイルの gzip 後 3MB、全体 150,000,000 バイト）。
- 処理時間: `graph` と `export` を合わせて 20分以内（試作の配置は全体で約1.5分）。

## テスト方法

- 単体テスト: ファミリーの決め方（親の決め方の3段階と循環）、`domKind` の同数の扱い、表示名の作り方、色の割り当て（50分野すべてに色があり、重複しない）。
- 小さなグラフ（3分野・30法令）でレイアウトの一連の処理を動かし、決定性と、出力の形が契約どおりであることを確かめる。
- 判定の数値（M1〜M11）の単体テスト: 手で置いた数点の配置で値が手計算と合う。円周に分野を並べた配置で M3・M4・M5 が不合格になり、分野を混ぜた配置で M1 が不合格になる。
- 分野の中の配置の単体テスト: 外への引きがすべて +x 向きの分野で、回転と寄せのあと法令の重心が +x 側に来る。柔らかい囲いのあと、どの法令も円の外に出ない。
- 全件で `validate-web-data.ts`。
- 受け入れ条件の数値は `data/graph/{snapshotId}/layout-report.json` に書き出して確かめる。
